## 진행 내용

### 시나리오 재구성

4회차 회고에서 "로컬 PC 쪽 로그온이 1초 만에 로그오프까지 기록돼 VM 세션과 겹치는 구간이 없었다"고 했다. 이번에는 두 머신 모두에 닫히지 않은 세션을 미리 만들어두고 로그를 수집했다.

시나리오 구성:

| 호스트 | 계정 | 방법 | 로그온 타입 | 예상 위험도 |
|---|---|---|---|---|
| VM (BOB-WIN11) | `alice` (관리자) | runas로 관리자 셸 유지 | 2 (Interactive) | CRITICAL |
| VM (BOB-WIN11) | `bob` (일반) | RDP로 접속 유지 | 10 (RemoteInteractive) | HIGH |
| VM (BOB-WIN11) | `svc_deploy` (서비스) | 예약 작업 실행 중 | 5 (Service) | CRITICAL |
| 로컬 PC | `bob` (일반) | 네트워크 드라이브 연결 유지 | 3 (Network) | LOW |

`bob`은 두 호스트 모두에 잡히는 계정이다. VM에서는 RDP(HIGH), 로컬 PC에서는 네트워크 접근(LOW)인데, 계정 단위로 묶으면 높은 쪽인 HIGH가 대표 위험도가 된다.

침해 시점을 양쪽 세션이 겹쳐있는 구간으로 잡고 분석을 돌렸다.

```bash
credscope analyze BOB-WIN11.evtx LocalPC.evtx \
    -t 2026-08-10T14:20:00 --kst
```

![CRITICAL/HIGH/LOW 가 모두 포함된 다중 호스트 통합 노출 리포트](/images/mogakco_29.png)

`alice`와 `svc_deploy` 두 계정이 CRITICAL, `bob`이 HIGH(VM의 RDP 세션이 대표값), 로컬 PC의 `bob` 네트워크 세션은 LOW로 세션 상세에 같이 보인다. 4회차에서 만들려다 실패한 장면이 이제 나왔다.

### README 작성

도구를 처음 보는 사람이 5분 안에 설치하고 실행할 수 있게 썼다.

```
## credscope

Windows EVTX Security 로그에서 로그온 세션을 재구성하고,
침해 시점에 LSASS 메모리에 비밀번호가 캐시되어 있던 계정을 자동으로 식별합니다.

## 설치

pip install git+https://github.com/me0w2en/credscope.git

## 사용법

credscope analyze Security.evtx -t 2026-08-06T09:43:00 --kst

## 옵션

-t, --compromise-time    침해 시점 (ISO 8601 형식)
    --kst                입력 시각을 KST(UTC+9)로 해석
    --format             출력 형식: table(기본) / csv / json
-o, --output             결과를 저장할 파일 경로
    --max-session-hours  로그오프 없는 세션의 최대 유지 시간(시간)

## 위험도 기준

| 위험도   | 조건                              |
|----------|-----------------------------------|
| CRITICAL | 관리자 권한 + 비밀번호 LSASS 캐시 |
| HIGH     | 비밀번호 LSASS 캐시               |
| MEDIUM   | 관리자 권한 (비밀번호 캐시 안 됨) |
| LOW      | 비밀번호 캐시 안 됨               |
```

## 회고

- 4회차에서 "양쪽에 로그오프하지 않은 세션을 만들어두고 재수집해야 한다"고 적어뒀는데, 이번에 그대로 따라 하니 바로 됐다. 문제가 뭔지 아는 상태에서 고치는 건 어렵지 않았다.
- `svc_deploy` 같은 서비스 계정이 CRITICAL로 잡히는 건 처음에 예상 못 했다. 서비스 계정도 Type 5(Service) 로그온은 비밀번호를 캐시하고, 4672(관리자 권한 부여)도 함께 찍히는 경우가 많다. 실제 환경에서는 이런 계정이 도메인 관리자 권한을 가진 경우도 있어서 놓치면 안 된다.
- 6회차가 마지막 회차라 전체를 돌아보면, 1회차에서 "어떤 로그온이 비밀번호를 메모리에 남기는가"를 정리한 게 나머지 5회차 내내 기준점이 됐다. 첫 회차에 개념을 정확하게 잡아두는 게 이후 구현에서 흔들리지 않는 이유가 됐다.
- credscope는 "어떤 계정을 리셋해야 하나"라는 질문에 로그만 있으면 2초 안에 답을 뽑아주는 도구가 됐다. 직접 쓸 일이 없기를 바라지만, 필요한 상황이 오면 꺼내 쓸 수 있다.
