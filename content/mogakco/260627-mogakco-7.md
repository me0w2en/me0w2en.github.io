## 진행 내용

### 위험도 분류 기준

2회차에서 만든 세션 목록에 대해, 침해 시점에 "이 세션의 비밀번호가 탈취 가능했는가?"를 판별해야 한다. 두 가지 조건을 조합해 4단계로 분류했다.

| 위험도 | 조건 | 의미 |
|---|---|---|
| **CRITICAL** | 관리자 권한 + 비밀번호 캐시됨 | 도메인 관리자급 계정이 메모리에 노출. 즉시 리셋 필요 |
| **HIGH** | 비밀번호 캐시됨 | 일반 계정이지만 비밀번호가 LSASS에 남아있었음 |
| **MEDIUM** | 관리자 권한만 있음 | Type 3(Network) 등으로 권한은 높지만 비밀번호는 캐시되지 않음 |
| **LOW** | 둘 다 아님 | 비밀번호 노출 위험 낮음 |

```python
def classify_risk(session: LogonSession) -> RiskLevel:
    if session.is_privileged and session.is_credential_cached:
        return RiskLevel.CRITICAL
    if session.is_credential_cached:
        return RiskLevel.HIGH
    if session.is_privileged:
        return RiskLevel.MEDIUM
    return RiskLevel.LOW
```

### 침해 시점 기준 활성 세션 필터링

침해 시점에 세션이 열려있었는지 알기 위해 2회차에서 구현한 `is_active_at()` 메서드를 활용해 필터링한다.

```python
def analyze_exposure(sessions, compromise_time):
    results = []
    for session in sessions:
        if not session.is_active_at(compromise_time):
            continue
        risk = classify_risk(session)
        results.append(ExposureResult(session=session, risk=risk, reason=...))
    results.sort(key=lambda r: list(RiskLevel).index(r.risk))
    return results
```

세 가지 경우를 처리한다:

- 로그온 ~ 로그오프 사이에 침해 시점이 있으면 → 활성 (비밀번호 노출)
- 로그오프 기록이 없으면 → 아직 열려있는 세션으로 간주 (활성)
- 침해 시점 이전에 로그오프했으면 → 비활성 (제외)

### CLI analyze 명령

침해 시점을 `--compromise-time`(축약형 `-t`) 옵션으로 입력받는다.

```bash
credscope analyze Security.evtx -t 2026-08-06T08:43:00
```

침해 시점에 열려 있던 세션만 남았다. 그 전에 끝난 로그온(`alice`와 `bob`의 초기 세션들)은 전부 빠졌다. 눈에 띄는 건 같은 `bob` 계정인데 RDP 세션(Type 10)은 HIGH, 네트워크 세션(Type 3)은 LOW로 갈렸다는 점이다. 같은 사람이라도 어떻게 접속했느냐에 따라 비밀번호가 메모리에 남는지가 달라진다는 게 결과로 보인다. 위험도 순 정렬과 등급별 집계도 의도대로 나왔다.

### 실제 로그를 넣어보고 드러난 문제

정작 CRITICAL로 올라온 두 건은 사람이 쓰는 계정이 아니다. `DWM-3`는 Windows가 화면을 그리는 데 쓰는 내부 계정이다. 2회차에서 만든 노이즈 필터가 `DWM-1`, `DWM-2`까지만 이름을 나열해뒀는데, RDP로 세션이 하나 더 생기면서 번호가 `DWM-3`으로 올라가 그대로 통과해버렸다. HIGH의 `UMFD-2`, `UMFD-3`도 같은 이유다.

"총 6개 계정 노출, CRITICAL 2개"라고 찍혀 있지만 실제로 확인해야 할 건 `bob` 두 건뿐이고 나머지 넷은 오탐이다. 리셋할 계정을 골라주는 게 이 도구의 목적인데 엉뚱한 데를 먼저 보게 만든다. 이름을 나열하는 대신 `DWM-숫자` 같은 패턴과 소속 도메인(`Window Manager`, `Font Driver Host`)으로 필터링이 필요하다.

집계 문구도 "6개 계정"이라고 하지만 실제로 세는 건 세션 수라, `bob` 한 사람이 두 번 계상됐다. 리셋 대상 계정이 몇 개인지를 알려주는 게 목적이니 계정 단위로 묶는 게 맞는 것으로 보인다.

## 회고

- CRITICAL/HIGH/MEDIUM/LOW 4단계 분류는 직관적이라, "CRITICAL부터 리셋하라"는 식으로 바로 쓸 수 있을 것 같다.
- 다만 테스트 20개가 다 통과해도 실제 로그에서는 오탐이 절반을 넘었다. 테스트에 쓴 이벤트는 내가 직접 만든 것이라 진짜 Windows가 뱉는 변종은 애초에 들어있지 않았다.
- 로그오프 기록이 없는 세션을 "활성"으로 간주하는 것이 보수적안 판단이지만, 오래전 세션까지 활성으로 잡힐 수 있다. 5회차 예외 처리에서 최대 세션 유지 시간을 설정하는 옵션을 고려해야겠다.
- 다음 회차에서는 여러 호스트의 EVTX를 통합 분석하고 CSV/JSON 리포트로 출력하는 기능을 구현할 예정이다.
