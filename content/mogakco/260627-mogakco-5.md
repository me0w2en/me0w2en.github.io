## 진행 내용

### 세션 빌더 핵심 로직

1회차에서 파싱한 개별 이벤트(4624, 4634, 4647, 4672)는 각각 독립적인 로그 항목일 뿐이다. 이번 회차에서는 이 이벤트들을 Logon ID를 기준으로 하나의 세션 단위로 묶는 세션 빌더를 구현했다.

동작 흐름:

1. 모든 이벤트를 시간순으로 정렬
2. **4624(로그온 성공)** → 새로운 세션 생성
3. **4634/4647(로그오프)** → Logon ID가 같은 세션에 종료 시각 기록
4. **4672(관리자 권한 부여)** → Logon ID가 같은 세션에 특권 플래그 표시

```python
def build_sessions(events: Iterable[LogonEvent]) -> list[LogonSession]:
    sessions: dict[str, LogonSession] = {}
    privilege_logon_ids: set[str] = set()

    sorted_events = sorted(events, key=lambda e: e.timestamp)

    for event in sorted_events:
        data = event.data

        if event.event_id == "4624":
            logon_id = data.get("TargetLogonId", "")
            account = data.get("TargetUserName", "")
            if not logon_id or not account or is_noise_account(account):
                continue

            session = LogonSession(
                logon_id=logon_id,
                account=account,
                domain=data.get("TargetDomainName", ""),
                logon_type=int(data.get("LogonType", "0")),
                logon_time=event.timestamp,
                source_ip=data.get("IpAddress"),
                is_privileged=logon_id in privilege_logon_ids,
            )
            sessions[logon_id] = session

        elif event.event_id in ("4634", "4647"):
            logon_id = data.get("TargetLogonId", "")
            if logon_id in sessions:
                sessions[logon_id].logoff_time = event.timestamp

        elif event.event_id == "4672":
            logon_id = data.get("SubjectLogonId", "")
            privilege_logon_ids.add(logon_id)
            if logon_id in sessions:
                sessions[logon_id].is_privileged = True

    return sorted(sessions.values(), key=lambda s: s.logon_time)
```

`privilege_logon_ids` set은 4672 이벤트가 4624보다 먼저 도착할 수 있기 때문에, Logon ID를 미리 기록해두고 이후 세션 생성 시 확인하는 방식으로 처리했다.

### 검증용 로그 만들기

구현한 코드가 실제 로그에서 동작하는지 확인하려면 로그온 타입이 골고루 섞인 이벤트 로그가 필요했기 때문에 Windows 11 가상머신에 테스트 계정 두 개(`alice`는 관리자, `bob`은 일반 사용자)를 만들고 로그온 방식을 하나씩 발생시켰다.

| 로그온 타입 | 만든 방법 |
|---|---|
| 2 (Interactive) | `runas`로 다른 계정의 명령 프롬프트 실행 |
| 3 (Network) | `net use`로 자기 자신의 공유 폴더에 접속 |
| 9 (NewCredentials) | `runas /netonly`로 다른 자격증명 지정 |
| 10 (RemoteInteractive) | 호스트 PC에서 원격 데스크톱(RDP) 접속 |

이렇게 쌓인 이벤트 로그를 `wevtutil` 명령어로 필요한 이벤트 ID만 추출하여 테스트 파일로 사용했다.

```powershell
wevtutil epl Security C:\evtx\Security.evtx /q:"*[System[(EventID=4624 or EventID=4634 or EventID=4647 or EventID=4672)]]"
```

### 노이즈 계정 필터링

내보낸 로그를 `parse` 명령으로 그대로 출력하면 아래와 같다.

![credscope parse 명령의 원시 이벤트 출력](/images/mogakco_19.png)

화면이 전부 `SYSTEM`, `LOCAL SERVICE`, `DWM-1` 같은 계정으로 채워져 있다. 사람이 로그인한 기록은 한 줄도 보이지 않는다. Windows는 서비스 시작이나 화면 그리기 같은 내부 작업에도 로그온 이벤트를 남기기 때문에, 실제 사용자 로그온은 이 사이에 파묻힌다.

이런 계정은 비밀번호 노출 분석에서 볼 일이 없으니 걸러냈다. 머신 계정은 이름 끝에 `$`가 붙는 규칙이 있어서 한 줄로 처리된다.

```python
NOISE_ACCOUNTS = {"SYSTEM", "LOCAL SERVICE", "NETWORK SERVICE",
                  "DWM-1", "DWM-2", "UMFD-0", "UMFD-1",
                  "ANONYMOUS LOGON", "-"}

def is_noise_account(account: str) -> bool:
    if account in NOISE_ACCOUNTS:
        return True
    if account.endswith("$"):  # 머신 계정
        return True
    return False
```

### CLI 서브커맨드 구조 변경

기존 CLI는 하나의 `parse` 명령만 있었지만, 세션 빌더 추가에 맞춰 서브커맨드 구조로 변경했다.

- `credscope parse <evtx>` — 기존처럼 개별 이벤트 출력
- `credscope sessions <evtx>` — 세션 단위로 묶어서 테이블 출력

`sessions` 명령을 실제 로그에 적용한 결과다.

![credscope sessions 명령의 세션 테이블 출력](/images/mogakco_20.png)

수백 줄이던 원시 이벤트가 18개 세션으로 줄었다. 앞에서 만든 로그온 타입 2, 3, 9, 10이 전부 잡혔고, RDP 접속(Type 10)은 접속한 PC의 IP까지 들어왔다. `alice` 세션에만 `Privileged` 표시가 붙은 것도 맞다. 관리자 그룹 계정이라 4672가 함께 찍힌 걸 제대로 물어왔다. `bob`의 Type 3(네트워크) 세션만 `Cred Cached`가 비어 있는데, 1회차에서 정리한 "네트워크 로그온은 비밀번호를 메모리에 남기지 않는다"는 기준이 적용된 결과다.

그런데 걸러졌어야 할 계정이 남아 있다. `DWM-3`, `UMFD-2`, `UMFD-3`. 필터 목록에는 `DWM-1`, `DWM-2`, `UMFD-0`, `UMFD-1`까지만 적어뒀는데, RDP로 접속하면 세션이 하나 더 생기면서 번호가 그 위로 올라간다. 이름을 통째로 나열하는 방식의 한계다.

같은 계정이 같은 시각에 두 줄씩 잡힌 것도 보인다. 관리자 권한으로 프로그램을 실행할 때(UAC) Windows가 일반 권한용과 관리자 권한용 토큰을 따로 만들면서 로그온 이벤트를 두 번 남기기 때문이다. 실제로는 한 번 로그인한 건데 두 세션으로 세고 있는 셈이다.

## 회고

- Logon ID 하나로 4624/4634/4672를 엮는 구조가 실제 로그에서도 그대로 동작했다. 다만 Logon ID가 재사용되는 경우(시스템 재부팅 후)에 대한 처리가 필요할 것 같다.
